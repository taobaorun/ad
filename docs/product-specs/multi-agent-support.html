Product specification · multi-agent foundation

让 AD 管理 Agent，而不是管理某一个 Agent

提案：新增稳定的 Agent Adapter 边界，把“配置、skills、plugins、项目目录、进程探测、激活与备份”抽象为能力；Claude Code 作为首个完整适配器，Codex 作为第二个适配器，未来 Agent 只实现适配器，不再复制整套 UI、store 和持久化逻辑。

1. Objective

AD 当前是 Claude Code 配置管理器。下一阶段需要支持 Codex，并为其他 coding agent 留出可验证、可扩展的接入方式。用户应能在同一项目下看到不同 Agent 的配置状态，选择一个 Agent 编辑或应用配置，并清楚知道哪些能力可用、哪些能力不适用。

用户故事

作为同时使用 Claude Code 和 Codex 的开发者，我可以按 Agent 管理配置，不会因为切换 Agent 而覆盖另一个 Agent 的文件。

成功体验

我能在一个统一界面里选择 Agent、查看其真实文件来源、应用 profile、管理可用 skills，并在不支持某能力时得到明确说明。

核心风险：不能把“同名字段”误认为“同义配置”。每个适配器必须声明文件格式、作用域、能力和写入策略；未知字段必须保留，未经用户确认不得跨 Agent 转换。

2. 领域模型

统一模型负责描述“可管理对象”，适配器负责描述“如何发现、读取和写回”。通用模型不包含 Claude 或 Codex 专属字段。

概念职责关键字段持久化
AgentId稳定标识一个 Agentclaude-code、codex、未来自定义 ID用户配置与历史引用
AgentAdapter发现、读取、写入、探测能力metadata、capabilities、locations、operations代码注册，不存运行态
AgentInstallation一台机器上的可用安装/配置根agentId、rootPath、source、status~/.ad/state/agents.json
AgentProfile针对某 Agent 的配置 recipeprofileId、agentId、layers、schemaVersion~/.ad/profiles/<id>.json
AgentProjectState项目与 Agent 的实际状态projectPath、agentId、files、lastApplied派生读取 + 审计记录
Capability声明可执行功能settings、skills、plugins、processDetection、launch适配器元数据
interface AgentAdapter {
  readonly metadata: AgentMetadata;
  readonly capabilities: ReadonlySet<Capability>;
  discover(context: DiscoveryContext): Promise<AgentInstallation[]>;
  readProjectState(projectPath: string): Promise<AgentProjectState>;
  applyProfile(input: ApplyProfileInput): Promise<ApplyResult>;
  inspect(path: string): Promise<InspectionResult>;
}

接口只是边界示意，最终签名应在规格批准后进入实施计划；不允许把任意 Agent 的全部行为强行塞进一个“settings JSON”接口。

3. 目标架构

统一层
  • Agent 选择、项目关联、profile 列表、备份、历史、错误展示。
  • 能力驱动 UI：未声明能力的 tab/action 不显示或显示 disabled reason。
  • 持久化按 agentId 隔离，禁止共享同一份 Agent-specific settings。
适配器层
  • 每个 Agent 独立处理路径发现、格式解析、原子写、作用域和进程探测。
  • 适配器必须报告“实际路径”和“来源”，支持用户审阅；多个 Agent 或多个发现来源指向同一真实安装时，统一层按 canonical identity 去重，只保留去重后的 canonical installation。
  • 新 Agent 不应修改已有 Agent 的业务命令和组件。
Codex 接入的当前设计假设

Codex 的具体配置位置、文件格式和可管理能力不在通用层硬编码。Codex adapter 首次运行时通过受限的 discovery 规则检查已知用户级/项目级位置，并把发现结果展示给用户确认；若官方约定或版本发生变化，只更新 adapter。

本规格不把 Codex 的模型名、权限字段、AGENTS.md 或其他文件直接映射为 Claude 的 ClaudeSettings。任何跨 Agent 转换都必须生成独立的目标配置，源 Agent 配置只读不改；如果目标配置已存在，必须先展示差异和无法转换字段，用户确认后才备份目标并写入，失败时恢复目标备份。

必须满足的行为

  • Claude Code 现有项目、profile、skills 和 legacy 激活行为不回归。
  • Codex 能被发现、启用/禁用，并在项目维度读取和保存其真实配置；配置、skills、plugins、进程探测和终端启动能力均达到对等支持。
  • profile 使用 (agentId, profileId) 复合身份，不同 Agent 不会发生内容串写；历史记录包含 agentId。
  • 每次写入前都产生 Agent-specific backup；写入失败不改变原文件。
  • 未知 Agent 或未支持能力会产生英文可诊断错误，UI 通过 i18n 展示可操作提示。
  • Claude Code 配置可转换为 Codex 配置，转换前展示差异，转换后可应用、备份和回滚；新增一个 stub adapter 可通过测试接入，而不需修改通用 UI 的分支判断。

5. Testing Strategy

测试重点是适配器隔离、数据安全和 schema 演进，而不是只验证 UI 是否能渲染。

Rust unit / integration
  • adapter registry、capability negotiation、路径 discovery、格式 round-trip。
  • 每个写入操作验证 backup、atomic rename、未知字段保留和失败恢复。
  • 使用 AD_HOME=<tempdir>，并按项目规范串行化 HOME 测试。
TypeScript / UI
  • agent-aware store 的选择、加载、错误和 capability gating。
  • Claude/Codex profile schema 的 parse、版本迁移和互不污染。
  • zh/en key 集合保持一致；所有用户文案无硬编码。
行为验证
  • 真实临时项目：发现 → 编辑 → 预览 diff → 应用 → 读取确认 → 恢复备份。
  • 未知文件、权限错误、外部修改、适配器不支持能力均需有明确结果。
  • 至少一条“新 stub adapter 接入”回归测试证明扩展点成立。

6. Boundaries

Always

  • 使用 agentId 做持久化隔离。
  • 写入前备份，使用原子写，记录 adapter 和真实路径。
  • 未知字段保留；跨 Agent 转换必须可预览。
  • 适配器错误带上下文，UI 文案走 zh/en i18n。

Ask first

  • 改变现有 Claude Code 文件位置或语义。
  • 引入数据库、新依赖或修改 Tauri 权限。
  • 把某个 Agent 的配置转换为另一个 Agent 的默认模板。
  • 删除用户文件、移除 legacy 行为或改变默认 Agent。

Never

  • 在通用 UI 中写 if (agent === ...) 的业务分支。
  • 未经确认覆盖另一个 Agent 的配置。
  • 把 API key、token 或 secrets 写入日志、规格 fixture 或错误。
  • 用静默 fallback 把不支持当成成功。
