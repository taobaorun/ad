# ExecPlan 执行计划规范

执行计划（ExecPlan）是用于管理复杂、多小时编码任务的设计文档。它是一个"活文档"，在实施过程中持续更新。

## 何时创建 ExecPlan

- 涉及 5+ 文件 / 多模块改动 / 架构变更：**必须**创建
- 涉及 2-5 文件、需要设计思考：**可选**创建
- 单文件修改 / 小 bug：**不需要**

## Tier 2 双格式：MD + HTML

ExecPlan 是 Tier 2 文档，**创建时同时生成两份**：

- `docs/exec-plans/active/<任务名>.md` — 执行真理源（live state）
- `docs/exec-plans/active/<任务名>.html` — 已批准的方案基线快照（评审版）

HTML 不是 MD 的机械翻译，借助可视化（文件树图、stepper、timeline、checklist）让用户更容易扫读和决策。HTML 由 `html-artifact` skill 生成（specs / plan 场景）。

### 生命周期

| 时刻 | 行为 |
|---|---|
| Stage 2 创建 | MD + HTML 同时生成 |
| Stage 2 评审循环 | 用户提修改 → MD 和 HTML **必须同步更新** |
| 用户批准 | HTML 冻结，底部追加 `Approved plan baseline (frozen at <时间戳>). Live execution state: see <md-path>` |
| Stage 3 执行 | 进展、决策、意外发现**只改 MD**，HTML 不动 |
| Stage 4 归档 | MD + HTML 一起移到 `completed/`，**HTML 不重渲** |

## 核心原则

- **自包含**：包含实施所需的所有知识和指令
- **是活文档**：随进展持续修订（MD 部分）
- **支持新手**：让不了解项目的人也能端到端复现
- **可验证**：每个步骤有可验证的完成标准

## ExecPlan MD 结构（必须章节）

```markdown
# <简短、行动导向的标题>

本 ExecPlan 是一个活文档。`进展`、`意外发现`、`决策日志`、`结果回顾` 必须随工作推进保持更新。

## 目的 / 全局视角
用几句话解释这次变更后用户能获得什么、如何观察到它在工作。

## 确认状态
- [ ] **待用户确认** — 评审 HTML 路径：`<path/to/html>`
- [ ] 用户已确认，开始执行（时间戳）

## 假设
列出隐含假设。不确定的东西必须列出来，不要沉默假设。

## 影响范围
将修改/新增哪些文件。建议在 HTML 里画文件树图。

## 关键决策
方案中值得注意的技术选型或取舍。如果有更简单的方案，说明为什么不用。

## 进展
- [ ] (待开始) 步骤一描述（验证标准：xxx）
- [ ] 步骤二描述（验证标准：xxx）

完成时用 `[x] (YYYY-MM-DD HH:MMZ) 步骤描述` 形式打勾 + 时间戳。

## 意外发现
- 发现：...
  证据：...

## 决策日志
- 决策：...
  理由：...
  日期/作者：...

## 结果回顾
完成时填写：实际效果、与目标的差距、遗留问题。

## 上下文和方向
像读者一无所知一样描述当前状态。命名关键文件路径。

## 工作计划
叙述编辑顺序，命名文件 + 位置 + 要做什么。具体、最小化。

## 验证和验收
描述如何启动 / 运行系统 / 观察结果。验收以行为表述，包含具体输入输出。

## 幂等性和恢复
如果步骤可重复，说明。如果有风险，给出回滚路径。

## 接口和依赖
要用到的库、模块、服务及其原因。指定里程碑结束时必须存在的类型 / 函数签名。

## 里程碑规划（如适用）
每个里程碑独立可验证、增量推进。
```

## 编码行为约束（执行期硬规则）

ExecPlan 进入 Stage 3 后，以下四条原则贯穿全程：

1. **先想后做** — 不确定就停下来说，不要沉默假设
2. **最小实现** — 只写解决当前问题所需要的代码
3. **精准修改** — 只触达与任务直接相关的代码，不顺手重构
4. **目标驱动** — 每步必须有可验证完成标准
