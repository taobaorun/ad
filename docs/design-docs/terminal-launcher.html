External Terminal Launcher

AD 在选中 project 后,通过用户配置的外部终端打开 claude,cwd 锚定到 project 路径。本文档记录 4 个 backend 的行为契约和实现取舍。

1

设计原则

不重新发明 env 注入

CC 启动时自动从 <project>/.claude/settings.local.json 顶层 env 字段加载环境变量(v0.4 per-project config model 落地)。launcher 只负责 cd + claude,不在 shell 命令里 export env。

单一职责。如果 launcher 自己 export env,会和 CC 的加载逻辑漂移,任何一边出 bug 都难定位。

窗口存活检测靠失败回退,不维护状态

每次按钮按下都是冷判断:用 pgrep 看进程在不在,在就尝试 AppleScript 复用窗口,失败立即降级到 "open 新窗口"。不维护 PID 或 socket 缓存。

维护状态需要监听进程退出、处理多窗口并存、跨 AD 重启持久化——所有这些复杂度换来的收益,只是少跑一次 pgrep。不划算。

每个 backend 自己消化平台差异

对调用方来说接口都是 launch(LaunchSpec) -> Result<()>。"新 tab 还是新窗口" / "AppleScript 还是 CLI" 这些细节藏在各 backend 文件里。

未来加 WezTerm / iTerm2 时,只需要新增一个 enum variant + 一个文件,不动其他实现。

3

为什么 Ghostty 每次都是新窗口

macOS Ghostty 在 CLI 层没有任何复用窗口开新 tab 的接口:

  • ghostty +new-window 报 not supported on this platform(只在 GTK/Linux 实现 IPC)
  • +new-tab 是内部 keybind action,无法从 CLI 调用
  • tab 复用唯一办法是 osascript keystroke 模拟 ⌘T,但需要把 osascript 加入 Accessibility 权限列表,而 osascript 不能干净地加入(权限对象错位)

结论:不做 hack。AD 直接走 open -na Ghostty.app --args -e zsh -lc "cd '<cwd>' && exec '<claude>'",每次开新窗口。

需要 tab/workspace 模型的用户切到 cmux backend——它的产品定位就是多 workspace,且自管 IPC,不需要任何系统权限。

shell wrapper 的作用

不直接 -e claude 的原因:

  • -e 走 /usr/bin/login -flp <user> <cmd>,会把 claude 当 login shell 参数而不是命令
  • -e 子进程不 source 用户 rc 文件,所以 claude 不在 PATH 里(homebrew/nvm/asdf 路径都没有)
  • --working-directory= 对 -e 模式不生效,exec 时 cwd 继承自父进程

因此包一层 zsh -lc:login shell 加载 rc → 拿到正确 PATH/env → 内部 cd + exec claude。

AD 同时用 SHELL -lc 'command -v claude' 预先 resolve claude 绝对路径作为兜底,避免 rc 加载失败时找不到。

4

为什么 cmux 透传 path

cmux 的产品模型自带 workspace / window / pane 三层概念,且 cmux <path> 已经做到:

  • cmux 没运行 → 启动 cmux 并打开 path 作为 workspace
  • cmux 已运行 → 在现有窗口里新开一个 workspace 显示 path

AD 介入会和它的产品行为冲突——比如"新窗口 vs 新 tab"在 cmux 里是用户用快捷键决定的,不是命令行参数。

UI 上需要明确告知用户:cmux backend 下"新窗口"开关不起作用。Settings 里加一行 helper text。

cmux backend 的用户前置条件

cmux 默认 socket access mode 是 cmuxOnly — 只接受 cmux 自己 fork 的子进程的 IPC 调用。AD 作为外部进程会被拒,报 ERROR: Access denied — only processes started inside cmux can connect。

用户必须在 cmux Settings → Socket Control 切换到 Automation mode(推荐,只放行同一 macOS 用户的外部 client,无密码),或 Full open access(不安全)。命令行写法:

defaults write com.cmuxterm.app socketControlMode automation
cmux reload-config

这是 cmux 的安全边界。AD 不试图代用户修改,而是在错误消息和 Settings hint 里明确告知。

cmux 可能保留上次 workspace

cmux 启动时会 restore 上一次 session 的 workspace。即使 AD 这次只创建 1 个 workspace,用户可能看到多个 — 那是 cmux 的 restore 行为,不是 AD 重复创建。

5

Custom 模板设计

两个占位符:

  • {{cwd}} → POSIX 单引号包裹的项目路径
  • {{cmd}} → POSIX 单引号包裹的 claude 命令

替换由 AD 做 shell-quoting,模板作者不用处理含空格或单引号的路径。替换后整串交给 sh -c 执行。

常见模板示例:

open -na WezTerm.app --args start --cwd {{cwd}} -- {{cmd}}
alacritty --working-directory {{cwd}} -e {{cmd}}

让用户写完整 shell 脚本太自由,quoting 翻车率高;只暴露两个占位符就够覆盖 95% 的终端。未来如果有 backend 需要更复杂的参数化(比如 split pane / profile name),再加新占位符不破坏现有模板。

6

错误反馈策略

  • 成功不弹 toast — 窗口本身就是反馈。多弹一次 toast 是噪声。
  • 失败用 inline error banner(ProjectDetail header 下方红条)— 比 toast 更显眼,且不会自动消失,用户能从容看错误内容。
  • 错误内容直出 anyhow message — 不做"友好化包装",二进制找不到时直接显示 ghostty: command not found,工程师一眼能定位。
7

未来扩展点

  • 新增 backend:加 enum variant + 新文件,大约 50 行
  • 启动参数化(claude --resume / 自定义 args):在 LaunchSpec 加字段,不影响接口
  • tray menu 直接打开终端:tray module 调用 terminal::launch 即可,不需要走 IPC
  • 切 backend 时验证二进制存在:可以加 which 探测,但不是默认行为(避免每次保存 settings 触发 IO)
