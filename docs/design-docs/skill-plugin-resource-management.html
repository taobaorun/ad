Skill / Plugin
资源中心与项目安装

AD 统一管理资源的身份、来源、兼容性和生命周期，但绝不统一或转换资源内容。所有安装都从资源中心进入，并在明确的项目与 Agent 作用域内，以软链接读取原始或受管 source checkout。

01 · Architecture

统一 lifecycle，不统一内容

核心层只持有资源身份、source binding、兼容性结果和安装账本；原始 Skill / Plugin 目录始终交给对应 Agent adapter 原样读取。

实线是 AD 受管控制流；虚线是外部观察边界。外部项不会反向进入 Resource Catalog。
D1 · Source binding

只抽象资源身份

复用 stable / physical root 和 validated manifest；不定义跨 Agent 的 Plugin component model。

D2 · Durable state

Catalog + Ledger 双层权威

Catalog 决定什么可安装；Ledger 决定哪些项目/Agent 安装由 AD 管理。

D3 · Adapter seam

兼容性与计划由 Agent 签发

frontend 不产生路径、目标或适配策略，只消费 sealed plan 和 limitation code。

D4 · Plugin

Claude direct-reference

Claude 通过项目级软链接与 LaunchRecipe 加载；当前 Codex Plugin 如实阻塞。

D5 · Removal

复用标准卸载

中心移除逐项目执行相同 uninstall；部分失败不回滚成功项，资源保持可管理。

D6 · Product surface

资源库与项目状态分开

顶级资源中心负责管理；项目页只聚焦 Installed、Available 与下一步操作。

02 · Durable model

四类状态，各有唯一职责

不依靠目录名或同名关系猜测。资源、安装、物理 ownership 与长操作被明确拆开，并由 receipt 串起。

CatalogSource

来源与稳定视图

Git 或 Local source，以及当前受验证的 stable / physical root。

  • source_id
  • source_type
  • SourceBinding
  • health / revision
CatalogResource

可安装资源

source-scoped 的 Skill / Plugin 身份及生命周期。

  • resource_id
  • kind + install_id
  • subpath
  • managed / suppressed
InstallationRecord

项目 × Agent 安装

资源落到具体 workspace 与 Agent 后的高层权威。

  • workspace_key
  • agent_id
  • target_claim_id
  • ownership record IDs
LifecycleOperation

跨项目移除进度

记录每个卸载目标的 durable state，支持断连、崩溃与重试。

  • operation_id
  • sequence / phase
  • per-item result
  • partial failure
关键唯一性约束

同一 source 内 (ResourceKind, install_id) 必须唯一；不同 source 的同名资源拥有不同 ResourceId，可以共存。真正的安装冲突由 (workspace, Agent, target_claim) 判断。

C

Claude Plugin 安装

  1. Validate — 读取原生 Plugin root 并校验本期 adapter contract。
  2. Link — 在 AD workspace runtime 创建指向 catalog 的单一软链接。
  3. Record — 写 InstallationRecord、ownership 与 enabled state。
  4. Launch — AD LaunchRecipe 追加 --plugin-dir <managed-link>。
X

Codex Plugin 阻塞

  1. Inspect — 当前 loader 只认 PluginStore 的 active installation。
  2. Reject copy — 原生 install 会复制 source tree，不符合中心更新传播。
  3. Reject scaffold — “真实目录 + 子项链接”无法保证任意结构更新完整传播。
  4. Report — 返回 unsupported_agent_capability，等待未来原生 direct-reference。
04 · Control flows

安装与移除都从 backend 权威开始

frontend 提交 ResourceKey、workspace revision、action 与 Agent selection；不提交 source path、marketplace stage 或 Agent target。

1

Project install

  1. Resolve — ResourceKey 反查 managed CatalogResource。
  2. Choose — 用户明确选择当前项目与 Agent。
  3. Inspect — adapter 返回 compatibility 与 target claim。
  4. Block or plan — unsupported / managed conflict / external conflict / sealed preview。
  5. Apply — ExecutionEngine 同一 journal 写 link、Agent state、ownership 与 ledger。
2

Git source update

  1. Stage — 获取新 generation，不改变当前消费者。
  2. Scan — 拦截重复 ID、非标资源与路径逃逸。
  3. Join — 对所有 active installation 重验 subpath 与 adapter compatibility。
  4. Switch — 全部安全后原子切换 current。
  5. Propagate — 项目 link bytes 不变，自动读取新内容。

中心资源移除状态机

managed

正常可安装、可管理；preview 只读取影响范围。

running

确认后持有 resource lease，逐项执行 standard uninstall。

partial_failure

成功项不回滚，失败项保留诊断；resource 仍 managed。

suppressed

零 active installation 后 CAS 提交；刷新与重启不自动恢复。

partial_failure → 用户显式 retry → 重新枚举真实 ledger → running；startup 只 reconcile，不自动继续破坏性写入。
S

Source removal 复用同一生命周期

  1. Preview — 汇总 source 下所有 managed Skill / Plugin 以及受影响的项目与 Agent。
  2. Confirm — 明确告知删除会使所有现有安装失效；取消不产生任何写入。
  3. Uninstall — 按资源、项目和 Agent 逐项调用标准卸载，并展示真实进度与失败项。
  4. Commit — 只有全部资源没有 active installation 后才移除 source catalog entry。
  5. Preserve — Local 原始目录与 Git checkout 内容都不删除；失败时 source 保持可管理并允许重试。
冲突没有“一键切换”

目标被另一份 AD 安装占用时，先展示其 source 并提供标准卸载；卸载完成后，用户再单独发起新来源安装。external 占位只允许重新检查。

05 · Migration & safety

兼容读取，显式写入，失败关闭

升级不在启动或 inventory 中静默搬移、重新链接或删除任何旧状态。所有迁移都绑定显式 mutation receipt。

M

Migration sequence

  1. Dual read — 将 skill_catalog.json v2 投影为新的 resource view。
  2. Reuse roots — 既有 Git skill-library binding 不移动、不复制。
  3. Explicit write — 第一次 catalog mutation 才 journaled 写入新 document。
  4. Lazy backfill — legacy Skill ownership在显式 install-state mutation 中写 ledger。
  5. Legacy Plugin — 旧 Codex copy 不改写；证据完整时只保留 uninstall。
S

Security authority

  1. No path IPC — project install caller不能提交任意路径。
  2. No execution on scan — 不运行 hook、script、package manager 或 Agent validator。
  3. Confinement — normalized relative path、no-follow 与 canonical root校验。
  4. Dual evidence — ledger + ownership同时有效才授予删除权。
  5. Stale rejection — preview revision、source identity、target digest 与 compatibility在apply重验。
持久操作与并发边界
  • Catalog write 使用 process-wide writer lock 与 monotonic revision CAS。
  • Source operation 同时锁定 source root；resource removal 持有 resource lifecycle lease。
  • Project install/uninstall 使用 workspace + Agent target locks，同一 physical target 不并发修改。
  • Git generation publish、current switch、catalog write 与 receipt 延续现有 finish-or-compensate journal。
  • 跨项目移除不追求全局原子；每项原子、整体 truthful，并能从 durable snapshot 恢复。

Final contract

资源是唯一安装来源，项目是唯一操作作用域。

中心决定“什么由 AD 管理”，项目与 Agent 决定“安装到哪里”。软链接让中心更新自然传播；Installation Ledger 和 ownership 让卸载、冲突和跨项目影响可证明；adapter 只在 Agent 原生能力允许时提供支持。
